# openpi 工具懒加载：对抗性评估报告（模拟 + 行业标准）

> 状态：设计评估（2026-08-13），配套 docs/tool-lazyload-design.md
> 方法：模拟各 LEVEL 实现 → 按行业权威标准逐层攻击 → 闭环/可靠性/稳定性分析
> 关键对抗发现（先给结论）：**懒加载收益 100% 取决于激活状态稳定性——震荡时缓存全失，成本反噬**（见 §4.1，实测数据建模）。

---

## 1. 模拟设定（被评估对象）

| LEVEL | 实现方式（模拟） | 工具 |
|---|---|---|
| **L0 常驻** | 现状不变（完整描述每轮注入） | tasks×3, goal×3, plan_ready, fd, rg（9） |
| **L1-入口** | 短描述常驻 + agent-type 枚举/schema 按需 | subagent_spawn, bg_start, workflow（3） |
| **L1-条件** | **名字+触发条件常驻** + 完整描述在实体活跃时注入 | wait/send/check/list/cancel, bg_status/list/kill/watch, workflow_status/stop（11） |
| **L2 按需** | 名字+一句话常驻 + describe_tool(name) 拉取 schema | ask_user, context_pivot, configure_my_pi_setup（3） |

**澄清设计**（对抗中修正）：L1-条件工具是"**名字+触发条件常驻** + 完整描述激活注入"——不是完全消失——**发现性（决策 1 信息）永不丢失**，只延迟决策 2 信息（完整 schema）。

## 3. 逐层级对抗评估

### 3.1 L0 常驻（9 工具）——攻击：现状是否值得保留

| 对抗点 | 攻击 | 裁决 |
|---|---|---|
| A1 fd/rg 是否真高频 | 若模型 80% 会话不用 fd/rg——常驻浪费 2×~200 tok | **部分成立**——但 fd/rg 与内核 read/bash 互补（文件发现是编码会话核心），且实测 openpi 增量大头在 subagents/workflows（运行时枚举），L0 合计仅 1.3-1.5k——**保留**，后续可用 session 记录实测频率再裁 |
| A2 tasks guidelines 压缩 | 3 条行为约束（"记录 claim 不验证"等）压缩后模型行为漂移 | **不压缩**——tasks 是高频且语义敏感（waitingOn/evidence 分类错误会破坏 ontology）——guidelines 是行为护栏，属决策 1 信息 |
| A3 常驻工具间的相互干扰 | 9 工具全量 = 模型选择噪声 | 低风险（现状已存在）——保留 |

**L0 裁决：无改动，风险最低。**

### 3.2 L1-入口（3 工具）——攻击：发现性缺口与安全边界

| 对抗点 | 攻击 | 严重度 | 缓解 |
|---|---|---|---|
| **B1 agent-type 枚举 defer 的发现缺口** | spawn 的 agent_type 参数枚举（explorer/implementer/…+能力表）被 defer 后——模型不知道有哪些 agent type 可选——**枚举值也是决策 1 信息**（"我能用哪种 agent"） | **高** | 枚举值列表（名字+一行）常驻（~15 值 × 8 tok ≈ 120 tok），**每值的能力细则 defer**——两段式（枚举常驻 + 细则按需） |
| **B2 安全边界丢失** | spawn 的 promptGuidelines（"只在可信目录"/"worktree 隔离"）短化后——模型绕过隔离启动 | **高（安全）** | 安全类 guidelines **永不 defer**（whitelist 类规则进短描述）；OWASP LLM07 对应——工具描述必须含安全约束 |
| B3 bg_start 默认值误用 | timeout/working_dir 默认语义短化后误传 | 中 | 参数默认值进短描述（一行） |
| B4 workflow 复杂参数 | phase/agent_type/pipeline 语义压缩后误构 | 中 | 同 B3——"关键参数一行 + 复杂语义 defer" |

**L1-入口裁决：可行，但 agent-type 枚举必须两段式（枚举常驻、细则 defer），安全规则永不 defer。**

### 3.3 L1-条件（11 工具）——攻击：信号、竞态、震荡（本层最大风险面）

| 对抗点 | 攻击 | 严重度 | 缓解 |
|---|---|---|---|
| **C1 激活信号准确性** | session-liveness 计数 vs 实际实体——事件延迟窗口：实体刚 settle 计数未更新（工具可见但调用失败）或刚 spawn 计数未更新（工具不可见无法 wait） | **高** | 信号用**已订阅的 manager 事件**（非轮询）——事件已同步（settle → notify 同步链实测）；仍保留窗口 ≤1 轮——**调用时实体不存在 → 友好错误（现状已有）**，错误信息引导"实体已结束" |
| **C2 激活震荡（flapping）→ 缓存全失** | 子代理快速 settle（连环 kill/短任务）→ 工具集在"完整/索引"间每轮切换 → 系统提示前缀每轮变化 → **prompt cache 全部失效**（实测建模：见 §4.1——震荡成本是稳定状态的 10x，比现状还贵 0.6 倍） | **严重（成本反噬）** | **单调化（hysteresis）**：激活后保持 ≥K 轮（如 3 轮）再失活；或激活后整轮 session 保持（L1-条件工具一旦激活到 session 结束）——**推荐：会话级保持**（工具集在 session 内单调不减）——稳定性 > 极限省 |
| **C3 能力闭环断裂** | wait/check 不可见时模型不知道"可以等待子代理"——用 bash 轮询/放弃——行为退化 | 高 | **名字+触发条件常驻**（~10 tok/工具 × 11 ≈ 110 tok）——模型知道存在与何时用——决策 2 信息激活时注入——闭环保持 |
| **C4 /resume 状态恢复** | 新 session 恢复旧子代理/终端——激活状态未同步 → 操作工具不可见但实体存在 → 无法 wait/cancel | 中 | resume 时从 manager view 重建激活集（view.list() 已有）；tasks 的 unsubSettled 模式可复用 |
| C5 实体存在但不可激活 | 实体在 manager 但在 UI 计数外（如 settled 待交付） | 低 | 用 manager 内部计数（含 settled）而非 UI 计数 |
| C6 恶意状态操纵 | 提示注入让模型 spawn 大量实体 → 工具全激活 → 载荷暴涨 | 中（安全） | 激活集与实体数线性相关——上限保护（≥3 实体时不再增描述，只更新计数行） |

**L1-条件裁决：可行，但必须加三条工程约束：①会话级单调（激活不减）②名字+触发条件常驻 ③计数有上限。**

### 3.4 L2 按需（3 工具）——攻击：延迟、模型能力依赖、静默丢失

| 对抗点 | 攻击 | 严重度 | 缓解 |
|---|---|---|---|
| **D1 多轮延迟** | 工具名→describe（1 轮）→调用（1 轮）——ask_user 需要用户决策时延迟 1 轮（用户等待） | 中 | ask_user 类**高频低延迟工具不放 L2**（改放 L0 短描述）——L2 只放真正低频（configure_my_pi_setup） |
| D2 弱模型不会 describe | 模型直接调用未 describe 的工具 → 参数错误 → 失败 | 中 | L2 工具的**参数 schema 保持最小可用**（describe 只补详情）；错误信息引导 describe |
| **D3 静默能力丢失** | 一句话描述的工具被模型忽略——用户需要"配置"时模型不调 setup（不知道存在/不知道何时用） | **高（最严重的失败模式——Anthropic deferred MCP 的已知权衡）** | 触发条件写进一句话描述（"改配置时用"）；**决策 1 信息永不省**——L2 本质只省 schema（决策 2）——若一句话不足以表达触发条件 → 该工具不该在 L2 |
| D4 内核不支持 | describe_tool 需内核改造——openpi 无法单侧实现 | 阻塞 | P3 提案；**P1/P2 不依赖 L2**——L2 是可选终态 |

**L2 裁决：仅 3 个真低频工具可进；ask_user 降级到 L0 短描述；触发条件必须进一句话描述。**

## 4. 全局对抗：成本经济学与闭环

### 4.1 【最重要发现】懒加载 vs prompt cache 的经济学对抗

实测建模（120 轮静态成本，cacheRead 定价 0.1x）：

| 场景 | 成本当量 | vs 现状 |
|---|---|---|
| 现状全量（前缀稳定） | 487.5k | 1.0x |
| 懒加载 + 状态稳定 | 30.0k | **0.06x（省 94%）** |
| 懒加载 + 每轮震荡 | 300.0k | **0.62x（省 38%——收益蒸发 90%）** |
| 懒加载 + 每 5 轮切换 | 84.0k | 0.17x |

**结论：懒加载的全部收益建立在"工具集前缀稳定"之上。震荡 = 缓存全失 = 每轮全价。**
→ 设计铁律：**激活状态会话级单调**（工具集一旦扩展，本 session 内不再收缩）——把"状态驱动"变成"会话级一次性决策"。

### 4.2 harness 能力闭环（26 工具可达性审计）

```
闭环四环（对抗审计）：
① 发现环：模型知道工具存在     → 名字+触发条件常驻（L1/L2 都满足）
② 获取环：模型拿到完整 schema  → L1 激活注入 / L2 describe
③ 执行环：调用成功             → 实体不存在时友好错误引导（现状已有）
④ 反馈环：实体状态变化→可见性  → manager 事件同步链（已实测）；会话级单调防震荡
```
**闭环断裂点**：仅 D3（L2 静默丢失）——缓解=触发条件进一句话；②获取环依赖内核（L2）——P3 前置。

### 4.3 可靠性审计

| 维度 | 攻击 | 状态 |
|---|---|---|
| 激活信号源 | 已订阅的 manager 事件（settle→notify 同步链，pi-backend 修复后无挂起） | ✅ 可靠 |
| 竞态窗口 | ≤1 轮（事件 vs 轮询）——调用失败有友好错误 | ✅ 可接受 |
| 幂等性 | 重复激活/重复注入——按会话单调后天然幂等 | ✅ |
| 恢复性 | /resume 重建激活集（view.list()） | ✅ 设计含 |
| 异常路径 | 实体管理器 dispose → 激活集清空（session_shutdown 联动） | ✅ 需实现时覆盖 |

### 4.4 稳定性审计

| 维度 | 风险 | 缓解 |
|---|---|---|
| 工具集变化频率 | 每轮变化 = 模型困惑 + 缓存失效 | **会话级单调**（变化 ≤1 次/session 方向） |
| 缓存稳定性 | 前缀稳定是收益前提 | 单调化 + L0 永远不动（L0 是全量前缀的锚） |
| 模型行为稳定性 | 工具可见集变化 → 计划漂移 | 工具集变更时**在系统提示标注可见集**（"当前可用：X 操作工具"一行） |

## 5. 风险矩阵与分阶段缓解

| # | 风险 | 严重度 | 概率 | 阶段缓解 |
|---|---|---|---|---|
| R1 | 激活震荡 → 缓存反噬 | 严重 | 中 | P2 会话级单调（强制） |
| R2 | agent-type 枚举发现缺口 | 高 | 高 | P1 两段式（枚举常驻） |
| R3 | 安全规则随短描述丢失 | 高 | 低 | P1 安全规则永不 defer |
| R4 | L2 静默丢失 | 高 | 中 | P3 触发条件进一句话；ask_user 降 L0 |
| R5 | /resume 激活集未恢复 | 中 | 低 | P2 view.list() 重建 |
| R6 | 计数无上限 → 载荷随实体数涨 | 中 | 低 | P2 描述上限（≥3 实体只更新计数） |

**推荐阶段（对抗修正后）**：
- **P1（openpi 侧）**：L1-入口两段式（枚举常驻+细则按需）+ 安全规则白名单 + ask_user 降 L0——不动 L1-条件
- **P2（openpi 侧）**：L1-条件上线——**会话级单调** + 名字常驻 + 激活集重建 + 描述上限——上线前用 SWE-bench 类任务回归（26 工具全路径）
- **P3（内核提案）**：describe_tool + deferred 标记——L2 才启动；P1/P2 不依赖

## 6. 结论

1. **对抗评估后方案存活**，但三处必须修正：①激活**会话级单调**（防缓存反噬——最大发现）②agent-type **枚举常驻**（防发现缺口）③安全规则**永不 defer**
2. **L1-条件是最优收益点**（无实体省 75% 且发现性不丢）——前提是单调化
3. **L2 是可选终态**（依赖内核），且只容纳 3 个真低频工具——ask_user 必须降级
4. **行业对标**：本方案的对抗约束（单调化、发现性常驻）正是 Claude Code deferred MCP 生产实践的隐含前提——我们显式化了它们
5. **验收**：每个阶段上线前，用 SWE-bench 类任务回归 26 工具全路径 + 120 轮缓存稳定性实测（前缀变化次数 ≤2）
